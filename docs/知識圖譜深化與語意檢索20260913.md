# D-006 深化：Entity/Event/Condition/Outcome、跨文件實體對齊、Tag 詞彙表、時間軸與本機語意檢索

2026-09-13。使用者明確要求擴張到「時間軸、實體候選、局部向量化／排序、LLM 關係抽取」與「D-006 再深一層：節點分解、跨文件實體對齊、正式因果驗證、tag 詞彙表、真正的圖資料庫／圖 UI」。LLM 關係抽取經詢問後使用者選擇暫不做任何 LLM 相關程式；本輪只做不需外部 LLM API 的部分。

## 範圍與原則

延續既有規則：沒有 LLM、沒有自動推論當作事實。新增的 Entity/Event/Condition/Outcome 節點與正式關係全部是人工從一筆**已接受**的 Claim 候選（cement/graph_extract.py）手動拆解／建立，不是自動 NLP／NLU 抽取；實體候選是規則式詞表比對，跨文件對齊必須人工明確指定，字串相同不自動合併。圖資料庫依 docs/知識圖譜銜接設計.md 原本的建議走 SQLite 的 nodes／relations／evidence／tags 結構，沒有引入額外的圖資料庫技術。

## 新增模組

### cement/graph_store.py

- **實體候選與跨文件對齊**：`extract_mentions()` 依 [config/entity-gazetteer.json](config/entity-gazetteer.json)（material／organization／standard／method／specimen 五類、中英文各數個詞，屬小型種子詞表，非完整 NER）掃描既有 graph_handoff 證據片段，產生 `entity_mentions`（規則命中候選，`review_status=pending`）。`link_mention()` 要求人工明確選「連到既有 entity_id」或「建立新實體」，字串相同不會自動合併；`mentions_for_entity()` 回傳該實體目前對齊到的所有文件版本——這才是跨文件對齊真正的產出：同一個人工確認的實體可以查到它出現在哪些不同文件。
- **節點分解**：`create_node(node_type, parent_candidate_id, payload, created_by)` 只接受 node_type ∈ {Event, Condition, Outcome}，且 `parent_candidate_id` 必須是**已接受**的 graph_candidates 列；payload 至少要有非空 `description`，Event 可選填 `event_time`（相對時間文字，如「day 7」，不猜日期）。
- **正式關係**：`create_relation()` 落實 config/graph-contract.json 的必要欄位（relation_type、evidence_ids、assertion_mode、polarity、conditions），relation_type 限定在 participates_in／occurs_under／has_outcome／claims_cause／supports／contradicts／concludes_from／precedes／describes；`same_event_candidate`／`tagged_with`／`broader`／`related` 分別由既有 candidate_relations、node_tags／tags 處理，避免重複建模。要求至少一個 evidence_id（契約原文：「每條語意關係都要引證據」）；from/to 端點可以是 Event／Condition／Outcome 節點、Claim 候選、Entity 或 DocumentVersion（後者只驗證非空字串，因為版本 id 是衍生值，未落地成獨立表）。
- **Tag 詞彙表**：SKOS-lite，`tags` 表有 pref_label_en／pref_label_zh／aliases／definition／broader_id／status；`create_tag()` 要求至少一個語言的 pref_label，broader_id 若指定必須已存在；`tag_node()` 可以把任何 node_id/node_type（含 Claim 候選）貼上 tag。
- **時間軸**：`timeline()` 刻意回傳兩個不合併的陣列——`event_times`（來自人工在 Event 節點填寫的 event_time，標示信心為「人工登錄」）與 `fetch_times`（來自 sources.checked_at，標示信心為「抓取時間非出版日期」）。合併成一條假裝精確的時間軸不誠實，所以沒有做。

### cement/vector_search.py（局部向量化／排序）

複用 D-005 [cement/semantic_benchmark.py](cement/semantic_benchmark.py) 已驗證過的 E5-small pooling 方法（query 前綴、mean pooling、L2 normalize），改造成可增量更新的檢索索引，而非一次性 benchmark：

- `document_embeddings` 表以 `document_id` 為主鍵，存 text_hash／model／revision／vector_json；`reindex()` 只處理 text_hash 或 model/revision 改變的文件，未變更的文件跳過——這是「向量庫可以增量更新」的實際落地，不是每次重建整庫。
- `semantic_search()` 對快取向量做 cosine（因為已 normalize，內積即 cosine）排序；可選 `rerank=True` 用 bge-reranker-v2-m3 對前 `rerank_pool`（預設 5）筆重排序，對齊 D-005／staged_classification.py「先 embedding 縮小候選，再 reranker 排序」的既有方法論，避免對整庫跑慢很多的 cross-encoder。
- 語料規模仍是幾百份文件等級，一次性全量 embedding 快取在此規模是合理選擇；這不是 TB 級別的向量化策略，README_總體架構.md 對全量向量化的既有警語仍然成立，只是本機語料還沒到那個規模。
- 模型載入與推論都延遲到函式內部 import，避免在沒裝 torch/transformers 的環境（例如跑 pytest 的預設 CI 情境）匯入本模組就失敗；測試也全部 monkeypatch `encode`／`_rerank`，不在快速測試套件裡載入真正的模型。

### cement/migrations.py

`ensure_column(db, table, column, declaration)`：用 `PRAGMA table_info` 偵測後 `ALTER TABLE ADD COLUMN`，取代先前在 graph_extract.py 內重複的手寫版本，供後續模組共用。仍不是正式 migration 系統，只處理「加欄位」這一種變更。

## 技術債處理

- **分頁**（延續前一輪 store.documents 的能力）：管理頁 index.html 的文件清冊改用 `/api/documents?limit=50&offset=` 分頁瀏覽，加上一頁／下一頁按鈕與頁碼；`/review` 的完整清單维持不分頁（審核流程需要看到全部可審核文件才能跳題、算配額，分頁會打斷既有工作流程，故意不動）。
- **Schema migration**：見上述 cement/migrations.py。
- **模型登錄／校準／延遲量測**：
  - cement/train.py 每次訓練除了覆寫 `models/classifier.joblib`（維持向後相容）外，另存一份到 `models/registry/<timestamp>-<hash8>.joblib`，並把 `{id, created_at, path, holdout_sources, classes, train_count, test_count, macro_f1, sklearn_version}` 追加進 `models/registry.json`；`GET /api/model-registry` 讀取。
  - `evaluation.json` 新增 `calibration.bins`：以測試集 top-label 信心切 5 個桶，回報每桶樣本數與實際正確率；明確加註 `n={test數}…是機制檢查，不是有效的校準估計`——目前測試集只有個位數樣本，這只是校準機制的線路測通，不是真正校準結果。
  - `/api/predict` 記錄延遲（`time.perf_counter`）到新表 `prediction_log`（latency_ms／predicted_label／top_score／created_at），`GET /api/predict-log` 讀取最近紀錄；只記統計欄位，不存輸入文字。

## 本機驗證

54 項 pytest 通過（44 既有＋10 新：tests/test_graph_store.py 5 項、tests/test_vector_search.py 5 項；另擴充 test_pipeline.py 既有訓練/預測測試的斷言，涵蓋 registry／calibration／predict-log，未新增測試函式）。

瀏覽器實測（真實模型推論，非 mock）：

- `/api/search/semantic-reindex` 對 392 份 parsed 文件建立快取，耗時約 61 秒（約 0.16 秒／份，與 D-005 記錄的 E5 中位數量級一致）；`/api/search/semantic?q=hydration+kinetics+of+cement+paste` 前五名皆為主題相關的水化動力學／水泥漿模型文件，管理頁的語意搜尋切換鈕操作同一結果。
- 管理頁分頁：513 份、每頁 50、共 11 頁，上一頁／下一頁按鈕與頁碼正確更新。
- `/graph` 掃描出 281 筆規則式實體候選；把兩份不同文件裡的「NIST」候選各自連結到同一個新建實體後，`mentions_for_entity` 正確回報「2 處提及、2 個文件版本」——這就是跨文件實體對齊的實際效果。過程中發現並修正一個真實 bug：連結後畫面重新整理的呼叫順序寫反（先重畫候選清單、後更新實體快取），導致剛建立的實體不會立刻出現在其他候選的「連到既有實體」下拉選單，需再操作一次才看得到；已把 `loadEntities()` 移到 `loadMentions()` 之前修正。
- 從一筆已接受候選拆出 Event 與 Outcome 兩個節點，用 `has_outcome` 建立正式關係（引用該候選的 evidence_id、assertion_mode=explicit_in_source）成功；建立 tag「shrinkage／收縮」與其 broader 為它的「drying shrinkage／乾燥收縮」成功。
- 在 Event 節點填 `event_time=day 7` 後，`/timeline` 頁面正確把它列進「已知事件時間」區塊，與「抓取時間」區塊分開顯示。

## 限制（誠實聲明）

- 實體詞表只有約 30 個詞、5 個類別，遠非完整 NER；規則對詞表以外的實體完全抓不到，也不做同義詞／縮寫的自動歸併（例如「Portland cement」與「波特蘭水泥」不會自動視為同一實體，需人工在建立/連結時自行判斷是否算同一個）。
- Event/Condition/Outcome 節點分解、正式關係、tag 貼標全部是人工填表，系統不驗證內容是否符合原文語意，只驗證欄位格式與是否引用真實存在的 evidence_id／節點/候選/實體 id。
- `same_event_candidate`（候選層級）與正式關係的 `claims_cause`（節點層級）是兩條不同的機制，尚未整合成單一因果驗證流程；「正式因果驗證」目前的意思是「用完整契約欄位人工記錄一條因果關係」，不是自動判定或統計驗證。
- 語意檢索沒有計算召回率／precision，只做了少量人工檢視相關性合理；rerank 路徑本次程式碼可運作但未在瀏覽器實測（bge-reranker 每份約數秒，rerank_pool=5 預期需十幾秒，超出本輪互動測試時間，之後應補測）。
- 時間軸的「已知事件時間」目前只有測試時手動填入的 1 筆，尚不能評估在真實資料上的覆蓋率。
- 這些全部是候選層級／人工紀錄層級的能力擴充，不是完整知識圖譜產品：跨文件因果驗證、圖形化探索 UI（目前只有簡單 SVG）、tag 的多對多查詢介面都還很初階。
