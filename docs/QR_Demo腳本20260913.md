# QR Demo 腳本

2026-09-13 建立，2026-09-13 更新以納入語意檢索、圖譜節點分解與時間軸。目的是求職展示 Python／JavaScript 全端與資料工程能力，不是展示已驗證的分類成效——分類成效仍待真實代表性資料（見 [D-007](README_總體架構.md#d-007-選樣偏差修正2026-09-13)／[D-008](README_總體架構.md#d-008-雙軌推進與配額延後2026-09-13)）。QR 只是集合入口，重點在後面的資料流程與架構。

功能已擴增很多（關鍵字＋語意搜尋、圖譜候選、節點分解、正式關係、跨文件實體對齊、tag 詞彙表、時間軸），全部走一輪需要約 5–6 分鐘；若時間有限，優先順序見「若時間不夠：精簡版」。

## 事前準備（不計入展示時間）

1. 啟動服務。同機展示用 127.0.0.1 即可；要讓手機掃碼須綁 0.0.0.0：

```powershell
Set-Location -LiteralPath 'D:\QR code design'
.venv/Scripts/python.exe -m uvicorn cement.api:app --host 0.0.0.0 --port 8011
```

2. 找本機區網位址（供手機同 Wi-Fi 連線；每次開機或換網路可能變動，展示前重新確認）：

```powershell
Get-NetIPAddress -AddressFamily IPv4 | Where-Object { $_.IPAddress -notlike '127.*' -and $_.IPAddress -notlike '169.254.*' }
```

手機與筆電須在同一網路；沒有登入與權限隔離，不要在公開網路上這樣展示。

3. 重建索引（新文件或重解析後才需要；語意索引第一次要跑全庫，數百份約 1 分鐘，務必在展示前先做完，不要在台上等）：

```powershell
.venv/Scripts/python.exe -m cement.search reindex
.venv/Scripts/python.exe -m cement.vector_search reindex
```

或在管理頁按「建立／更新語意索引」按鈕，一樣需要先做完再上台。

4. 圖譜候選、實體候選最好也在展示前先掃過一次，讓 `/graph` 頁面已經有東西可以直接展示，不用臨場等 API：

```powershell
.venv/Scripts/python.exe -m cement.graph_extract extract
```

實體候選掃描目前只有 API：`curl -X POST http://127.0.0.1:8011/api/graph/entity-mentions/extract`（或在 `/graph` 頁面按「掃描實體候選」）。

5. 建議展示前就先手動做出至少一組完整案例，臨場只需要「秀出來」而不用現場一步步建立（現場建立也可以講解，但比較花時間）：
   - 接受 1–2 筆候選，並用其中一筆拆出 Event＋Outcome 節點、建一條正式關係。
   - 把同一個實體（例如「NIST」）在兩份不同文件的候選都連結過去，讓 `/graph` 頁面的「已對齊的實體」能秀出「N 處提及、N 個文件版本」。
   - 建一個 tag 及其 broader（例如 shrinkage → drying shrinkage）。
   - 在某個 Event 節點填 `event_time`（例如「day 7」），讓 `/timeline` 頁面「已知事件時間」不是空的。
   - 本機開發資料庫目前已經有上述範例（2026-09-13 測試時建立），若展示機器就是同一台不需要重做；換機器或資料庫被清空過則要重跑一次。

6. 開啟 `http://127.0.0.1:8011/`（或改用區網位址）確認頁面與 QR 圖正常顯示，再開始計時。

## 腳本（約 5–6 分鐘）

| 時間 | 內容 |
|---|---|
| 0:00–0:20 | 開場：水泥領域文件工作台原型；QR 是集合入口，重點是後面的資料流程與自訓分類模型架構，不是 QR 本身的花樣 |
| 0:20–0:50 | 掃 QR（或直接開網址）進管理頁：說明「收集公開文件、確認用途、建立可追溯分類資料」；指出目前文件數與狀態分布，翻一頁分頁按鈕展示規模化準備 |
| 0:50–1:30 | 關鍵字搜尋：輸入例如「hydration」，說明搜尋刻意不用分類篩選——避免分類誤判造成永久漏檢；勾選「語意搜尋」再查一次同樣的詞，說明這是本機真的跑 embedding 模型（不是雲端 API），可以抓到用詞不完全一樣但語意相關的文件 |
| 1:30–2:10 | 開啟 `/review`：示範選一份文件、看片段預覽、選用途、填審核者與群組；強調人工標籤與規則建議分開、來源隔離避免版本／近似文件洩漏 |
| 2:10–2:50 | 開啟 `/graph` 上半部：候選審核（因果詞句候選，全部待人工接受或拒絕）＋跨文件事件關聯的 SVG 雛形圖 |
| 2:50–3:50 | `/graph` 下半部：從已接受候選拆出 Event／Outcome 節點、建一條正式關係（強調 evidence_ids、assertion_mode 都要填，不能空口說白話）；秀「已對齊的實體」區塊——同一個實體對到多個文件版本，這是跨文件對齊的重點；秀 tag 的 broader 階層 |
| 3:50–4:20 | 開啟 `/timeline`：說明刻意不把「人工登錄的事件時間」和「爬蟲抓取時間」合併成一條假精確的時間軸 |
| 4:20–5:00 | 收尾誠實聲明：目前分類成效只做過內部小樣本診斷（n=12，macro-F1 僅供流程驗證，不是可信賴的成效數字）；圖譜/實體/tag 全部是人工從已接受候選手動建立，不是自動 NLP／LLM 抽取；正式成效需要真實代表性資料，仍在規劃中。求職重點是工程落地：可重跑爬蟲、資料治理、來源隔離訓練、API／前端、測試覆蓋 |

### 若時間不夠：精簡版（約 3 分鐘）

保留 0:00–1:30（開場＋管理頁＋關鍵字/語意搜尋）與 2:10–2:50（`/graph` 候選審核），跳過節點分解／實體對齊／tag／時間軸的詳細操作，改成口頭一句話：「候選接受後還能進一步拆成結構化事件、跨文件對齊實體、建立 tag 詞彙表、放進時間軸，畫面在 `/graph` 和 `/timeline`，時間夠的話可以現場展示」，直接跳到收尾聲明。

## 已知限制（主動說明，不要等被問到）

- 分類分數未校準，API 固定 `review_required=true`；目前唯一的成效數字是 n=12 小樣本診斷，不是可信賴的準確率。
- 沒有真實公司／研究資料夾快照，代表性測試集尚未建立（D-007）。
- 圖譜候選是規則式因果詞候選句；Event/Condition/Outcome 節點與正式關係都是人工手動拆解建立，系統不驗證內容是否忠於原文語意，只驗證欄位格式與是否引用真實存在的 id。
- 實體詞表只有約 30 個詞、5 個類別，遠非完整 NER；跨文件對齊需要人工逐一連結，不會自動判斷「這是不是同一個實體」。
- 語意檢索沒有量測過召回率／precision，只有少量人工檢視相關性合理；rerank（bge-reranker）路徑本次只有程式與 mock 測試通過，未在瀏覽器實測，單次查詢預期要十幾秒。
- localhost 展示僅同機可用；跨裝置展示需同網段，且本機服務沒有登入或權限隔離，不能對外公開部署。
